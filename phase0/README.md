# ゲーム攻略くん Phase 0 検証ツール（Phase0Probe）

設計書 v2 の「Phase 0：実現性の検証」で確かめる4項目だけを調べる、小さなコンソールツールです。
**ゲーム攻略くん本体（認識・学習・UI）はまだ実装していません。**

| # | 検証項目 | 主に使うAPI |
|---|---|---|
| 1 | WGC で対象ウィンドウを前面・背面でキャプチャできるか（比較用に PrintWindow も） | Windows.Graphics.Capture（ウィンドウ単位）、PrintWindow(PW_RENDERFULLCONTENT) |
| 2 | 入力①②③が、それぞれ前面・背面で受け付けられるか | ①PostMessage WM_KEYDOWN/UP、②ViGEmBus 仮想 Xbox360 パッド、③SendInput |
| 3 | 最小化したときにキャプチャと①入力がどうなるか | ShowWindow、WGC、PrintWindow、PostMessage |
| 4 | 物理入力を検出して AI の入力ループを止められるか | WH_KEYBOARD_LL / WH_MOUSE_LL（INJECTED フラグ）、RawInput（RIDEV_INPUTSINK、hDevice） |

> ⚠️ **この exe はまだ Windows 実機で一度も動かしていません。** ビルド（Linux 上での win-x64 クロスビルド）が通ることまでしか確認していません。
> 初回実行で不具合が出る可能性があります。そのときは画面のエラー表示と `results\` フォルダをそのまま送ってください。

---

## 安全面の方針

- ゲームのメモリ読み取り、内部変数の取得、DLL の注入、ゲームファイルの解析は**一切行いません**（`OpenProcess` も `ReadProcessMemory` も使っていません）。
  対象ウィンドウは、タイトル・クラス名・プロセス名・ウィンドウの位置だけで特定します。
- 各テストの前に内容を表示し、`y` を入力したときだけ実行します。
- **③SendInput の背面テストでは、あなたが使っているアプリに誤入力しないよう、テスト用の「ダミー窓」を前面に出してから送ります。**
  送信する直前にも前面ウィンドウを確認し、想定と違うウィンドウが前面なら送信を中止します。キーを離す操作だけは、押しっぱなしを防ぐために必ず送ります。
- ダミー窓は届いたキーを記録して表示するだけで、キーを受けても何も実行しません。
- 低レベルフックは**観測のみ**です。入力を握りつぶしたり書き換えたりはしません。
- 管理者権限は要求しません（asInvoker）。

## 動作環境

- Windows 11（Windows 10 2004 以降でも動く想定ですが、WGC の黄色枠を消す機能は Windows 11 でしか使えません）
- 64bit 版
- .NET のインストールは不要です（ランタイムを同梱した単一 exe です）。
- ②を試す場合のみ ViGEmBus ドライバが必要です。導入されていなければ②は「利用不可」と記録して自動でスキップします。**このツールはドライバのインストールを行いません。**

## 使い方

1. `phase0-probe.zip` を展開し、`bin\Phase0Probe.exe` を任意のフォルダに置きます。
   SmartScreen の警告が出たら「詳細情報 → 実行」を選んでください（署名なしの exe のため）。
2. トルネコを**ウィンドウモード**で起動し、ダンジョン内の安全な場面（敵が近くにいない場所）で、メニューを閉じた状態にしておきます。
3. `Phase0Probe.exe` をダブルクリックで起動します（またはコマンドプロンプトから実行）。
   起動時に引数を指定することもできます:
   `Phase0Probe.exe --target トルネコ --key Escape --close-key Escape --pad Y --pad-close B --wait 900 --hold 80`
4. メニューで次の順に操作します。
   - `L`: ウィンドウ一覧を表示
   - `S`: 対象を選択（一覧の番号、タイトルの一部、プロセス名、`0x…` 形式の HWND のいずれか）
   - `K`: キー設定。**メニューを開くキーと閉じるキーをあなたが指定します**（ツール側では決め打ちしません）。
     キー名の例: `Escape` `Enter` `Space` `Z` `X` `A` `S` `Up` `F1` `Back` `VK:0x1B`。パッドのボタン名の例: `A` `B` `X` `Y` `Start` `Back`
   - `A`: テスト1〜4を順番に実行（各テストの前に確認があります）。個別に `1`〜`4` も選べます。
   - `Q`: 終了（レポートを保存します）
5. テスト中にツールが前面ウィンドウを切り替えます。自動で切り替えられなかったときは「〇〇をクリックしてください」と表示されるので、表示に従ってクリックしてください。
   **テスト中（特に③とテスト4の校正中）はキーボードとマウスに触れないでください。** 触った場合は結果に「物理入力あり」と記録されます。
   コンソールで入力を求められたら、先にコンソールウィンドウをクリックしてから入力してください。

## 各テストの内容と判定基準

### テスト1: キャプチャ（前面・背面）
- 前面: ゲームを前面にして `RateSeconds` 秒（既定5秒）WGC のフレーム数を数え、WGC と PrintWindow で PNG を保存します。
- 背面: ダミー窓を前面に出してゲームを背面にし、同じことを行います（ダミー窓がゲームに重なることもあります）。
- 「真っ黒」の判定: 平均輝度 < 8 かつ 輝度の標準偏差 < 4。
- 判定
  - ✅ OK: 背面でも WGC の画像が黒くなく、計測中にフレームの更新があった
  - ⚠️ 一部可: 画像は取れたが更新が0（画面が静止していたか、ゲームが背面では描画を止めている）。または WGC は駄目で PrintWindow なら取れた
  - ❌ NG: WGC も PrintWindow も黒か、取得できない
- 注意: **WGC は画面が変化したときにしかフレームを届けません。** 静止画面ではレートが 0 に近くなるのが正常です。キャラクターが足踏みしているなど、動きのある画面で測ってください。
  背面の WGC 画像にダミー窓が写っていなければ、「ほかのウィンドウに隠れていても取得できる」ことの確認になります。

### テスト2: 入力 ①②③ × 前面・背面
各方式・各モードで、次の順に行います。
1. 入力なしで 0.5 秒間隔に2枚キャプチャし、画面の自然な変化（ノイズ）を測る
2. 開くキーを送り、`WaitAfterInputMs`（既定 900ms）待ってからキャプチャ
3. 閉じるキーを送り、同じだけ待ってからキャプチャ
- 変化画素: RGB のいずれかの差が `PixelThreshold`（既定24）を超えた画素
- しきい値 = max(`MinChangedRatio`（既定0.3%）, ノイズの変化率 × 3 + 0.2%)
- **受理**: 開いた後の変化率がしきい値を超え、閉じた後に送信前とほぼ同じ画面へ戻った（WGC と PrintWindow のどちらかで検出できればよい）
- **要復旧**: 画面は変化したが元に戻らなかった（受理として数えますが、画像で目視確認してください）
- **反応なし**: しきい値を超える変化がなかった
- 方式ごとの判定
  - ①②: ✅ 背面でも受理 / ⚠️ 前面のみ受理 / ❌ 両方とも反応なし
  - ③: ✅ 前面で受理し、背面ではゲームに届かない（＝想定どおり。背面のときはダミー窓がキーを受け取ったことが記録されます） / ❌ 前面でも反応なし
- そのほかに記録する項目: 前面ウィンドウが最後まで維持されたか、ダミー窓に漏れたキー（①②の背面で漏れていれば警告）、フックから見えた自分の注入の数、テスト中の物理入力の有無
- ②で使う仮想パッドはシステム全体に見えるデバイスです。パッドを読むほかのアプリにも見える可能性があります。また、パッドの接続をゲーム起動後にしか認識しないゲームもあるので、反応がなければゲームを再起動してもう一度試してください。

### テスト3: 最小化
- 通常時に数秒計測 → 最小化（自動で `ShowWindow(SW_MINIMIZE)` するか、自分で最小化ボタンを押すかを選べます）→ 最小化中に計測
- 記録する項目: WGC のフレーム数・最終フレーム時刻・ContentSize・セッションが閉じたか、PrintWindow の結果と真っ黒判定
- 最小化中に①で開くキーを送る → `SW_SHOWNOACTIVATE` で元に戻す → 最小化前の画面と比べ、画面が変わっていれば「最小化中の入力が処理された可能性あり」とする → 変わっていれば①で閉じるキーを送る
- 判定は ℹ️ 情報です（良し悪しではなく、挙動の記録が目的です）。WGC は最後のフレームを保持し続けるだけのことがあるので、**最終フレーム時刻が最小化した時刻より前なら、それは止まった画面です**。

### テスト4: 物理入力の検出
- 校正（5秒、触らない）: ダミー窓を前面にして、AI 入力ループのつもりで無害なキー F24 を署名付きの SendInput で 200ms ごとに注入します（同時にダミー窓へ PostMessage も送ります）。
  フックで `LLKHF_INJECTED` と署名（dwExtraInfo）を見て「自分の注入」と分類できたか、RawInput で hDevice=0（注入）と分類できたか、物理入力と誤って判定しなかったかを確認します。
- 本番（最大30秒）: ループを動かしたまま、あなたがキーを押すかマウスを動かします。物理入力を検知した系統、その内容、検知してからループが止まるまでの時間（ms）を記録します。
- 判定: ✅ 物理入力で停止し、校正中の誤検知が0で、自分の注入も正しく識別できた / ⚠️ 停止はできたが誤検知や識別漏れがあった / ❌ 30秒以内に検知できなかった

## 出力（結果の返し方）

実行するたびに、exe と同じフォルダの `results\yyyyMMdd-HHmmss\` に次のファイルを作ります。
- `report.md`: 人が読むためのレポート（判定の一覧、環境、各テストの数値、画像へのリンク）
- `report.json`: 同じ内容を機械で読める形にしたもの
- `*.png`: 前面・背面・最小化中のキャプチャ、送信前後の画像、差分マスク（変化した画素を赤で表示）

**返し方**: その `results\yyyyMMdd-HHmmss\` フォルダを丸ごと zip にして送ってください。
少なくとも `report.md` と `report.json` があれば分析できます。PNG にはゲーム画面しか写りませんが、背面テストの画像にはダミー窓など前面にあったウィンドウが写り込むことがあるので、送る前に中身を確認してください。

## 既知の制約・未検証の点

- **Windows 実機では未実行です。** WGC の初期化（D3D11 と WinRT の相互運用）、ViGEm のネイティブ DLL の展開、フォーカスの制御は、実機で初めて動作を確認することになります。
- Windows Terminal で実行すると、ツールからコンソールを前面に戻せません。入力を求められたら、自分でクリックしてから入力してください（従来のコンソールホストでも同じ操作で問題ありません）。
- 自動で前面にできないときは、クリックするよう表示します（Windows の前面化の制限によるもので、回避するための入力の注入は行っていません）。
- ゲームが管理者権限で動いている場合、①③は UIPI によって遮断されます（本ツールは一般権限で動きます）。
- ①PostMessage は、ゲームが DirectInput や RawInput、GetAsyncKeyState でキーを読んでいると無視されます。それ自体が検証したい結果です。
- 画面差分による判定は簡易的なものです。ゲーム側のアニメーションや BGM 演出で画面が変わると誤判定することがあるので、必ず PNG を目視で確認してください。
- 仮想パッドの方式は ViGEmBus（開発終了）だけを試します。後継ドライバの調査は別途行います。
- WGC の黄色い枠を消す処理は Windows 11 でしか効きません。失敗しても検証には影響しません。

## ソースとビルド

- `src/`: C# / .NET 8（`net8.0-windows10.0.22621.0`）、WinForms（ダミー窓とメッセージループ用のみ）、依存パッケージは `Nefarius.ViGEm.Client 1.21.256` だけです。
  - `Capture.cs`: WGC と PrintWindow / `InputBackends.cs`: ①②③ / `InputMonitor.cs`: フックと RawInput / `Probe.cs`: テスト本体 / `Report.cs`: JSON・Markdown 出力
- ビルド: `./build.sh`（`dotnet publish -c Release -o ../bin` を実行します）。Linux 上で `EnableWindowsTargeting=true` を使い、win-x64 の自己完結型単一 exe を作ります。
