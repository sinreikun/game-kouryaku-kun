## 主な変更（v0.11.0 → v0.12.0）

- 不具合の修正（v0.11.0 の診断 zip で見つけたもの）: v0.9.0 で作った分割（m1 → m1#v7）が、読み直しの機能（v0.10.0）より前だったため一度も読み直されていなかった。分割に「読み直し済み」の印を付け、起動時に印のない分割を読み直す（実機の DB の写しで 30 手を読み直し、残り 0 を確認）
- 分割の一生: 次の画面の分布の違い（ベイズ因子 10 以上）でも分ける。分けた後の経験が粗いノードと「同じ」と強くいえる（ベイズ因子 1/10 以下・3 操作以上・各操作が分割のときの 2 倍の回数）ときは取り消し、元の記録を書き換えずに読み直しで戻す。取り消した後は、取り消した後の観測だけで分け直しを判断する。出来事は state_split_events に残す
- 読み直しの高速化: 状態の索引で、そのノードに関わる手だけを読む（全履歴の走査と同じ結果を試験で確認）
- 観測の確かさ: 判断ごとに、見た目の状態・画面の種類の割り当ての距離の比、判定に使った画面の古さ、境目の近くかどうかを残す。境目の近くの観測は、予測との比較には入れるが、内部モデルを作り直すきっかけにはしない
- 並びの評価: 並びを実行した結果を予測と比べて記録し（sequence_executions）、最近の実行で予測が外れ続けた並びは休止する（古い実行は数えないので、また候補になれる）
- 判断の記録の長期の運用: 1 万手ごとの区間で、ノード×操作×決め方の要約を追記する（元の記録は消さない・書き換えない。何度実行しても同じ）。健全性レポートに増え方の見込みを出す
- DB の点検の道具: `ゲーム攻略くん.exe --harness --inspect <memory.sqlite> [summary|decisions|revisions|splits|sequences|provenance ノード [操作]]`。読み取り専用で開き、移行も書き込みもしない
- Viewer: 右側の各欄を見出しのクリックで畳む・開く。状態は data\ui-settings.json に保存して次の起動で戻す（学習 DB ではない。表示だけ）
- 実機確認の整理: 「画面を保存（知覚器の評価用）」と「記録を書き出す」を廃止（実機確認は診断 zip だけで、画像を使わないため）。代わりに手探り探索の「実行時間」を選べるようにした。健全性レポートに 1 手あたりの処理時間（前回までとの比較）・表示の設定の保存を自動判定する項目を足し、項目名から版の番号を外した
- 過去の実機の記録（診断 zip を展開したもの 11 件）を real-machine-archive/ に変更せずに保管（回帰試験用。意味は読み取らない）
- DB スキーマ v9（v8 から自動移行。移行前にバックアップ）

## 実機データ

- 実機データを見たか: **はい（v0.11.0 の診断 zip の DB とログの写しのみ。画像なし）**。v8 → v9 の移行 92ms、読み直していない分割 1 件（30 手）を読み直して 0 件、健全性の総合 OK、1手あたりの処理時間の中央値 160ms（件数と時間だけ。内容は解釈していない。件数に合わせた調整はしていない）

## 疑わしいもの・判断の記録

- 取り消しの判定は分割ノードと粗いノードの次のノードの分布だけで行う。結果の種類（変化の有無など）の違いだけで分けた分割は、次のノードが同じなら取り消されうる（そのときは再び証拠がそろえば分け直す）
- 境目の幅（±25%）は汎用の値。境目の近くの観測の割合は記録して健全性レポートに件数を出すだけで、良し悪しは判断しない
- 判断の記録は 1 万手あたり約 10MB 増える。要約は追記だけで、元の記録を消す処理は入れていない（消すかどうかは利用者の判断が要る）
- 読み取り専用で DB を開いても、SQLite の WAL の作業ファイル（-shm）ができることがある（本体の DB の中身は変わらないことを試験で確認）
