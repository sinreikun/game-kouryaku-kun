## v0.29.0 の変更（Observation Layer ブロック 1〜4。拘束仕様 docs/observation-layer-spec.txt・設計 docs/observation-layer-design.md）
- 構造化した観測（schema 1）: 1 手ごとに global（状態名・色の分布の群・矩形の配置・見た目の状態・前景の鍵）・regions（16×12 の変化区画のつながりと追跡 ID・区画の因果）・text（行ごとの observed/inherited・前の手との差・数字の系列）・temporal・provenance を作り、memory.sqlite v17 の structured_observations に保存。まだない層（entities・relations・appearance）は not_implemented と明示。旧経験には行を作らない（legacy）。
- 1 手 = 1 完全な観測: 文字の読み取りを待ってから次の手を決める（読み取り中で読まない手をなくした）。速さは差分（画素が同じ区画は継承）・矩形の読み直し・キャッシュで。継承と未観測を区別。
- 健全性: 「1 手 = 1 完全な観測」「変化領域の追跡」。

## v0.28.2 の変更
- 次の画面の不確かさ: +1 の擬似観測は直接観測した次の画面と「まだ見ていない」にだけ置く。弱い事前の推定の重みは、直接見ていない次の画面なら「まだ見ていない」に足す。重み 0.04 の推定でも次の画面の種類ごとに +1 が付き、不確かさが 1 に張り付いていた。
- 手が起こす文字の変化の値打ち: 区画ごとの（手の割合 − 基準）に、その区画が変わるかの 2 値の不確かさ（もう 1 回試して分かる量）を掛ける。確かに予測できる変化は値打ちを失う。観測としての文字の変化・手が起こした分の記録は変えない。

## v0.28.1 の変更
- 待つ手の情報の値打ち（WaitInformation）: 成分ごとに「入力なしの観測の不確かさ（既存の 2 値の Dirichlet 情報量）× この画面で手の後にその変化が起きる割合（Jeffreys）」。成分は画面の変化・別の画面への移り・画素の区画（最大）・文字の区画（最大）。合計 1 − Π(1 − 成分) を既存の不確かさの項（重み 0.5）に入れる。固定の確率・新しい重みはない。待つ手の観測が増えれば自然に下がる。
- decision_scores に待つ手の成分（wait_visual・wait_leave・wait_pixel・wait_text）を追加。
- 点数の項ごとに、選んだ手の項の割合で「画面が変わった（短期）」「遷移の図の新しい辺」「新しい画面（長期）」を配って数える。前半と後半の項の割合も記録。重みは変えない（設計は design-component-value.md）。
- 健全性: 「待つ手の情報の値打ち」「点数の項ごとの短期の変化と長期の寄与」。

## v0.28.0 の変更
- 手の選び方の内訳: 毎手 `decision_scores`（全候補の新しさ・行き先の発見・離れる・画面の変化・文字の変化・情報・不確かさ・行き先の掛け算・行き詰まり・差し引いた入力なしの変化と、最終点・確率・選んだ理由）を記録。目的・並び・続ける手・人の手の時も同じ式の内訳を付ける。記録は乱数を使わず、選ぶ手は変わらない（テストで確認）。
- 区画ごとの因果（RegionCausality）: 画素 16×12・文字の配置 8×6 の区画ごとに、待つ手での変化と、手の種類ごとの変化の割合を数える。手の種類で割合が違うか（ベイズ因子 ±ln10）で「手で変わる区画」「手によらない区画」を分け、手によらない区画はその割合を基準にする（待つ手の基準が先・なければ最も変わりにくい手の割合を上限に）。
- 文字の変化: 観測としての「文字が変わった」と「手が起こした文字の変化（確からしさ付き）」を分けて持つ。点数の文字の項は後者。v0.27.3 の揺れの除外と全体の読み直しによる安定化をやめ、画素が動いていない所の文字の差も変化として数える（数は pixel_unconfirmed として記録）。
- 前景の鍵の文字の配置から、手によらないと分かった区画の行を除く（観測・状態の文字の記録からは除かない）。
- 文字の変化と次の遷移の関係（TextTransitionLink）を画面ごとに数えて記録（予測にはまだ使わない）。
- 健全性: 「文字の変化のうち手が起こした分と手によらない分」「画面の区画の見分け」「文字の変化が次の遷移の手がかりになるか」「手の選び方の内訳の記録」。

AI が画面の情報だけでゲームを遊ぶアプリ「ゲーム攻略くん」の途中版です。
`GameKouryakuKun.exe`（WPF）は、ゲーム画面を見ながら事前知識なしの「手探り探索」を動かします。1手ごとに、次の画面を経験から予測し、結果と比べ、予測の外れで内部モデルを直しながら操作を選びます。記録（観測→行動→結果・判断の理由）は `memory.sqlite` に残ります。ゲームの知識は使いません。

```
GameKouryakuKun-Bootstrap/
├─ ゲーム攻略くん.exe             起動ツール（毎回これを起動。本体の更新では置き換わらない）
├─ app/                           初期の本体 GameKouryakuKun.exe（以降は自動更新）
├─ runtime-manifest.json          .NET の取得元・版・サイズ・SHA-512/SHA-256・ライセンス
├─ THIRD_PARTY_NOTICES.txt
├─ profiles/torneko-remaster/profile.json
└─ README.md
初回起動後に増えるもの:
├─ runtime/                       .NET（約180MB）。消すと次回起動時に取り直します
├─ updates/                       更新確認用の一時ファイル
└─ data/                          記録・ログ（更新しても消しません）
```

## 自動更新

1. 起動ツールが `https://raw.githubusercontent.com/sinreikun/game-kouryaku-kun/main/release/latest.json` を取得します。
2. フィールド: `protocol`（1）・`version`・`sha256`・`bytes`・`url`（GitHub Releases の https）。
3. 導入済みより新しければ `url` の zip をダウンロードし、SHA-256 とサイズを照合してから `app\` へ原子的に入れ替えます（zip のルート = `app\` の中身）。
4. ネットに失敗しても、既存の本体があればそれで起動します（ログに残します）。
5. 起動ツール自身の更新はこの仕組みに含めていません。必要なときはブートストラップを取り直してください。

引数: `--offline`（更新確認しない）/ `--repair`（本体とランタイムを強制取り直し）/ `--check`（状態表示のみ）/ `--verify` / `--cleanup`。

開発者向け公開手順: `./build.sh` のあとリポジトリ直下で `../tools/publish_release.sh`（`app-update-<版>.zip` を GitHub Releases に上げ、`release/latest.json` を main へ推す）。

> ブートストラップ / app-update の SHA-256 は `SHA256SUMS.txt` に載せています。

| 上部のボタン | ゲームに接続／▶開始／⏸一時停止（再開）／■停止／緊急停止／OCRテスト／セットアップ／診断データを書き出す。オプション: 実行時間（なし・10〜60分）、占有モードの許可、手数上限（0 = なし）。2段目: Human Control と中立のキー名のボタン |

右のパネルのうち **目的 は「未実装」**と表示されます。「仮説」は AI が今もっている「この画面でこの操作をすると次はこの画面」という見込み（確かめ中・作り直した直後・確か など）、「新発見」はこの回に見つけた画面・分割・操作の並び・パターン・予測の作り直しです（表示だけで、操作の選び方には使いません）。

## 実機での確認（v0.19.0）

確認項目はプログラムが自動で判定し、診断データの zip の `health.txt` に PASS / WARN / FAIL / NOT_TESTED で出します。画面を見て報告していただく必要はありません。

### A. 手探り探索・10分（必須）

- **モード**: 手探り探索
- **設定**: 実行時間 **10分**、手数上限 0、占有モードの許可 オフ。
- **手順**:
  1. ゲームを**ウィンドウモード**で起動します（どの画面からでもかまいません。**始める前にセーブデータのバックアップをおすすめします**）。
  2. `ゲーム攻略くん.exe` を起動し、上の設定で「▶ 開始」→ OK。ゲームは背面のまま別のアプリで作業していてかまいません（最小化はしないでください）。
  3. 開始から 5 分ほどたったら「Human Control（人間が操作）」を押し、中立のキー名のボタンを好きなように 5 回ほど押してから、もう一度「Human Control」を押して自動に戻してください（押すボタンはどれでもかまいません。動作の確認のためで、正解を教えるためではありません）。
  4. 10分で自動で終わったら「診断データを書き出す」を押します。zip がクリップボードに入るので、送り先にそのまま Ctrl+V で貼り付けて渡してください（貼れないときは `data\exports\diag-*.zip`）。
  5. （見た目の確認・任意）Human Control のボタンが ON／OFF で分かるか、グラフで「すべて重ねる」を選べるかを見てください。報告は要りません。
- **理由**: 入力方式の選択（A だけで選ぶ）と送信の失敗、画面の反応（B。参考）、待つ手と入力なしの変化の記録、行動の出どころ（agent／human）の記録と DB の一致、Human Control の切替、自己生成の目的の作成と割合・記録の出どころ、1手サマリー・成長グラフの材料、DB スキーマ v10 への移行、予測の記録、時間切れの割合、1手あたりの処理時間、ユーザーの作業との分離を、健全性レポートで自動判定するためです。

### 停止・一時停止のふるまい（参考）

| 操作 | ふるまい |
|---|---|
| 「⏸ 一時停止」 → 「▶ 再開」 | 橙の帯「一時停止中: 手動」が出て入力が止まる。再開で続行する |
| ゲームを最小化 → 元に戻す | 橙の帯「ゲームの最小化」が出て止まる。元に戻すと自動で再開する |
| ゲームを前面にしてキーを押す | 「ユーザー操作」で止まり、5秒間何も操作しなければ再開する |
| 背面のまま別アプリで作業する | 止まらない |
| Ctrl+Shift+F9、または「緊急停止」ボタン | 赤の帯「緊急停止しました」が出て、すぐに入力が止まる |
| どの操作でも画面が変わらない状態が続く | 止まらない（未知の画面の性質として記録する）。止まるのは入力の送信そのものが続けて失敗したときだけ |

### C. OCR 部品の導入（任意。前回までに済んでいれば不要。いまの探索は OCR を使いません）

1. 「セットアップ」を開きます。次の2つの部品が「未導入」と表示されます。

   | 部品 | 版 | ライセンス | 取得元 | サイズ |
   |---|---|---|---|---|
   | ONNX Runtime | 1.20.1 | MIT | GitHub（microsoft/onnxruntime）のリリース zip | 約63MB（展開後は必要な4ファイルだけ） |
   | PaddleOCR モデル（PP-OCRv5 mobile det + rec + 辞書 + 日本語文字一覧）【推奨】 | ppocrv5-mobile-rapidocr-3.4.0 | Apache-2.0 | ModelScope の RapidAI/RapidOCR v3.4.0 | 約21MB |
   | PaddleOCR 日本語モデル（PP-OCRv4 det + japan rec + 辞書）【予備】 | ppocrv4-rapidocr-3.4.0 | Apache-2.0 | ModelScope の RapidAI/RapidOCR v3.4.0 | 約14MB |

   v5 が導入済みなら v5 を使います。v5 がなければ v4 を使います。
   v5 の認識モデルは多言語用です。簡体字（例: 满）が出ないように、出力する文字を v4 の日本語辞書にある文字（と英数字・かな・全角記号）に限っています。
   また、信頼度 0.5 未満の行は除外します。地形の模様を文字と誤検出したものを落とすためです。除外した行数は結果の詳細に出ます。

2. ライセンスの同意にチェックを入れ、「未導入をすべて導入」を押します。
   - 途中で「中断」を押すかネットを切ってから、もう一度導入してください。途中から再開すること（`Range` 指定で続きから取得すること）を確認します。
   - 導入後にもう一度押すと、何もダウンロードせずに終わります。
   - 「完全検査」を押すと、全ファイルの SHA-256 を計算し直します。
3. 「OCRテスト」を押します。今のゲーム画面の文字を読み、枠と文字列を表示します。
   - エンジンは「自動」（PaddleOCR → Windows 内蔵の順）、PaddleOCR、Windows 内蔵から選べます。
   - Windows 内蔵 OCR で日本語を読むには、Windows の言語設定に日本語（OCR 機能を含む）が必要です。
   - 「全エンジンで比較」を押すと、PaddleOCR と Windows 内蔵 OCR の結果を色違いの枠で並べて表示します。
   - 数字を含む行には、数値トークンへの分割も表示します（例: `AB|#15|/|#15`）。
     OCR がするのは文字列と数値の抽出までです。文字の意味は AI が経験から学ぶ方針なので、OCR では意味付けしません。
4. 結果を送ってください。「診断データを書き出す」で作った zip（`data\exports\diag-*.zip`）だけを送ってください（画像は入っていません）。
   - DB は使用中でも `-wal` の内容まで含めてコピーされます。前回の zip は `-wal` が欠けていたため、冒険 #5 の後半が DB に見えていませんでした。

## データの置き場所と記録内容

```
data/
├─ app.sqlite                    アプリDB: ハードウェア・取得/入力プローブ・入力方式の選択履歴・導入した部品（v0.14.1 までの互換性テストの記録も残ります）
├─ app.sqlite.bak-*              自動バックアップ（7日ごと、マイグレーション前。最新5個）
├─ ui-settings.json              表示の設定（右側の欄の畳む・開く）。学習 DB とは別。壊れていたら .broken-日時 に退避して既定の表示で始める
├─ profiles/torneko-remaster/
│   ├─ profile.json
│   ├─ memory.sqlite             経験DB（スキーマ v12）: 連続履歴（行動の出どころ agent／human つき）・自己生成の目的の記録・入力なしの変化・画面ごとの動き続ける所・遷移・画面の種類・見た目の状態と分割（状態と出来事）・読み直し・弱い事前の推定・判断の記録と要約・内部モデルの修正・並びの候補と実行 ほか
│   ├─ diagnostics.sqlite        v0.14.1 までの分離試験の記録（あれば）。学習には使わない
│   ├─ memory.sqlite.bak-*       自動バックアップ（1日ごと、マイグレーション前。最新5個）
│   ├─ screenshots/yyyy/MM/..    1手ごとの縮小画像（過程データ。冒険が終わると自動で削除。DB の記録は残る）
│   └─ recordings/run-N/         v0.11.0 までの「画面を保存」の残り。7日たつと自動で削除
├─ components/                   セットアップマネージャが導入した部品と manifest.lock
├─ cache/downloads/              ダウンロード途中のファイル（*.part。再開に使う）
└─ logs/app-*.jsonl              アプリのログ
```

- DB は WAL モードで、スキーマの版は `PRAGMA user_version` と meta 表で管理します。版が上がるときは、先にバックアップを取ってから前方向にだけ移行します。自分より新しい版の DB は開きません。
- `app.sqlite` が壊れていた場合は、`.broken-*` に退避して作り直します。`memory.sqlite`（学習の記録）には影響しません。
- 前回、正常に終了しなかった実行は、次回起動時に `crash` として閉じます。
- 学習 DB の点検は、診断データの zip の健全性レポートで行います（v0.12.0 のコンソールの点検の道具はハーネスと一緒に廃止しました）。

## 安全設計

- AI が使う情報はウィンドウのキャプチャ画像だけです。OCR に渡すのもキャプチャ画像（`Frame`）だけで、入力の型をテストで固定しています。
- 禁止API検査（`ForbiddenApiTests`）を拡張しました。全製品 DLL（Core・Windows・Storage・Setup・Ocr・App）のメタデータを検査します。
  - P/Invoke の宣言は `Native.cs` だけです。
  - ネイティブライブラリの動的読込（`NativeLibrary`）は `OrtNative.cs` だけで、読み込むのは導入済みの `onnxruntime.dll` だけです。`LoadLibrary` / `GetProcAddress` は引き続き禁止です。
  - ネットワーク通信（`HttpClient` など）はセットアップマネージャ（`GameKouryakuKun.Setup`）だけです。
  - プロセスのメモリ・ハンドル・モジュールにアクセスする API、レジストリ、ゲームファイルへのアクセスがないことも検査します。
- セットアップマネージャは、exe に埋め込んだマニフェストだけを信頼します。https 以外の URL、`..` を含むパス、64桁でないハッシュは読込時に拒否します。
  - ダウンロードしたファイルは SHA-256 を照合してから、作業フォルダから原子的に置き換えます。失敗した場合は元の版を残します。
  - マニフェストの署名検証はまだありません。
- Profile に書けるのは、ウィンドウ条件・中立の名前のキー割当・禁止キーだけです（キーの意味・表示名・攻略知識・画面の配置・手順は書けません）。
- 制約の静的検査（`ConstraintAuditTests`）:
  - 本体のコードと UI（Core・Storage・Ocr・App・Windows・Setup、XAML を含む）と Profile の文字列に、対象ゲームの語やゲームの意味を前提にした語がないこと
  - 識別子に、意味を前提にした語（death・enemy・menu・attack など）がないこと
  - Core の数値の既定値に「根拠:」の注記があること
  - Profile に診断用の既知操作の欄がないこと。手の選択の処理に、人間の手を模倣・報酬とする語がないこと（成長の計器は表示用）。人向けの名前の表を説明層だけが触ること
  - 本体が評価用の正解データを読まないこと。セーブステート・巻き戻し・乱数取得らしき記述がないこと
  - 今の版の自己監査記録（`source/audit/v0.19.0.md`）があること
  - 系列の学習に実行単位・冒険などの区切りを渡さないこと。識別子に excursion・episode・anchor などの区切り・操作対象を前提にした語がないこと
  - 診断データの zip に画像を入れないこと
  - 表示の設定（右側の欄の畳む・開く）を、記録・学習・行動の選択の処理が参照しないこと。表示の設定が学習 DB に触れないこと
  - 分割の取り消し・読み直しが、直接の記録（連続履歴・遷移の記録）を書き換えないこと。DB の点検の道具が読み取り専用であること
- DB は、見た目の分類の欄に意味ラベル（「敵」など）を入れられない制約付きです（`mobile` / `static` / `unknown` だけ）。
